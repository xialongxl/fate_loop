## 一、这个项目是什么

纯文字、模组驱动、**确定性**的 Roguelike 自动战斗工具。

玩家不操作战斗。玩家做的事是：**编排技能序列**（GCD 循环队列 + oGCD 优先级槽），然后让角色自动打，观察结果，回去改序列。战斗过程是纯函数：给定 `(seed, 序列配置, 内容模组)`，逐帧结果必然一致，1x / 4x / MAX 三种倍速下的最终状态**逐字节相同**。

技术栈：原生 JS（ESM，无框架）+ Vite + Vitest + Howler（音频，可选）。无 TypeScript，用 JSDoc 标注类型。UI 是手写 DOM + 模板字符串，地图用 SVG。

**为什么强调确定性**：这是整个项目的立项卖点。种子是复现整局的完整凭据，玩家可以抄下种子在别处重现同一局。所有涉及随机、时间、浮点的改动都必须先想清楚是否破坏这一点。详见「五、不可违反的内核不变量」。

## 五、不可违反的内核不变量

改代码前必须理解这五条。违反其中任何一条，确定性就崩了，而且**测试不一定立刻报错**（会在别的种子、别的倍速下才暴露）。

### 1. 三流随机分派

`prng.js` 用 `deriveSeed(masterSeed, streamName)` 把主种子派生成互不干扰的独立流：

- **map 流** —— 地图生成
- **battle 流** —— 战斗内随机（暴击、随机目标、随机 Buff）
- **player 流** —— 玩家开局 seedBonus

**规则**：绝不跨流借随机数，绝不在流内插入或删除一次 `next()` 调用而不评估影响。战斗流的调用次数必须与倍速无关。UI 想要随机数（比如打乱展示顺序），用 `Math.random()`，不要碰 PRNG 流。

### 2. 绝对到期时间戳

冷却与 Buff 存的是**绝对到期虚拟时刻**（`readyAt`、`expiresAt`），不是剩余时间。

**为什么**：剩余时间需要每帧递减，递减次数依赖帧数，帧数依赖倍速 → 倍速会改变结果。绝对时间戳只需比较 `virtualTime >= readyAt`，与推进步长无关。

**规则**：任何新增的计时字段都必须用绝对时间戳，不许写「剩余 N 毫秒」。

### 3. 时间量必须是 STEP_MS 整数倍

所有技能施法时间、冷却、Buff 持续都必须对齐到 `STEP_MS`。模组加载时的 `normalize` 会强制这一点，`tests/unit/mod-loading.test.js` 有对应断言（「官方内容的全部时间量都是 STEP_MS 整数倍」）。

**规则**：新增内容时别写 `cooldown: 2500`，先确认能被 `STEP_MS` 整除。

### 4. 属性单一数据源

`derived.js` 的注释写得很清楚：玩家的 `maxHp / attack / defense / critChance` **从不手写**，一律由 `(exp, equipment, seedBonus)` 经 `recalcPlayer` 重算。存档只存 `exp`、装备、当前 `hp`。

调用时机：升级、穿脱装备、强化、读档、进入战斗前。

**这条已经被违反了**，见缺陷 #1（商店永久属性提升会被 recalc 抹掉）。这是我在核查中实测确认的最严重逻辑 bug。

### 5. 音频永不影响逻辑

`AUDIO_PLAY` 契约返回 `undefined`、不消费随机数、sink 抛错不向上传播、sink 为 `null` 时静默丢弃。`tests/unit/contracts.test.js` 有四条测试锁定这个行为。

**规则**：不要让音频调用出现在会影响状态的表达式里。

### 平局打破规则

oGCD 候选排序是 `(槽位优先级降序 → 技能自带优先级降序 → skillId 字典序)`。字典序那一档是**必须的**：没有它，同优先级技能的执行顺序会依赖 `Map` 迭代顺序，而那是实现细节，不可依赖。

oGCD 抢占作用域是「每实体每步至多一个」，**不是全局一个**。

### P0-3：修复商店永久属性被抹掉（真实 bug，已实测）

`shopItems.js` 里 6 个 `kind: 'upgrade'` 商品直接写 `state.player.maxHp += 60` 这类语句。但 `maxHp` 是派生值，下一次 `recalcPlayer` 会用 `(等级, 装备, seedBonus)` 重算，永久提升**凭空消失**。

我写了临时探针实测确认：

```
{ before: 325, afterBuy: 385, afterRecalc: 325 }
```

花 40 碎片买的「磐石之核」，一次重算后归零。受影响商品：`shop.stat.maxHp` `shop.stat.attack` `shop.stat.defense` `shop.stat.balanced` `shop.stat.glass` `shop.stat.bulwark`。`event.well`（饮下井水 +40 maxHp）同理。

**修法**（推荐第一种）：

1. 在 `player` 上加一个 `permanentBonus: { maxHp, attack, defense, crit }` 字段，与 `seedBonus` 同级参与 `derivePlayerStats` 的加总；商品改成写 `permanentBonus`。这条最符合单一数据源原则，且天然进存档。
2. 或者把这些商品改成发装备（`getShopGear` / `purchaseGear` 已实现，见 P1-3），彻底取消「永久属性商品」这个品类。

改完必须补测试：买 upgrade 商品 → `recalcPlayer` → 属性仍在。

### P1-2：等级解锁未在运行时生效

**要做的**：
- 启动时构建一次 unlock table，注入 `sequenceScreen`
- 在序列编辑的写入路径上拒绝未解锁技能（UI 层给出锁定态，`is-lock` 这个 class 已经在代码里用了）
- 决定要不要在 scheduler 里也做一道防御性校验。我倾向要，理由是存档可能来自旧版本或被手改

解锁分档逻辑：前 `STARTER_SKILL_COUNT` 个技能 1 级解锁，其余在 `2..SKILL_UNLOCK_MAX_LEVEL` 之间均匀铺开。接线前记得确认 `main.js` 里的 `DEFAULT_GCD_SEQUENCE`（`blade.jab` / `slash` / `riposte` / `momentumStrike` / `cleave`）和 `DEFAULT_OGCD_SLOTS`（`ogcd.emergencyHeal` / `suddenStrike`）**全部在 1 级可用**，否则新游戏一开局就是非法序列。

- `RARITIES` 的 `orbSlots` 字段（宝珠系统）无任何消费者 —— 要么实装，要么从常量里删掉，留着会让后来人以为有这个系统

### P1-4：对话框系统的三个问题

**（a）Promise 永久挂起（真实 bug）**：`format.js#createConfirm` 传的是 `{ closeOnBackdrop: false }`，但 `dialog.js#open` 解构的参数名是 `{ onClose, backdrop, wide }`。参数名不匹配 → `backdrop` 取默认值 `true` → 点背景会关闭弹窗但 **不 resolve promise**，`await createConfirm(...)` 永久挂起。统一参数名即可。

**（b）ESC 与焦点陷阱是空头承诺**：`dialog.js` 的注释声称支持 ESC 关闭和焦点陷阱，实际**没有任何 keydown 监听**。全项目 grep `Escape` 零结果。这是无障碍缺陷（键盘用户无法关闭弹窗），要真做：加 keydown 监听 + `Tab` 循环 + 打开时记录 `document.activeElement`、关闭时还焦点。

**（c）两套对话框并存**：新 `ui/dialog.js`（零引用、缺 `openSummary`）与旧 `ui/panel/summary.js`（有 `openSummary`、`main.js` 在用）。接线时把 `openSummary` 迁到新 `dialog.js`，然后删旧的。

### P1-5：暂停功能不存在

引擎**没有 `pause()` / `resume()`**。`GAME_STATUS.PAUSED` 只出现在 `main.js` 的标签映射里，**从未被写入过**。没有 `visibilitychange` 处理（切标签页战斗继续跑），没有 P 键绑定。

实装时注意：暂停必须是「停止推进 `virtualTime`」，不能是「继续推进但不结算」，后者会破坏确定性。

### P1-6：没有胜利结局

游戏目前是无限层。`summary.js` 支持 `outcome: 'victory'` 但没有任何代码传入，`history` 里的 outcome 只可能是 `'death'`。

需要产品决策：设终点层（比如 30 层打完通关）？还是无尽模式 + 里程碑？这个决定会影响 `history` 屏的设计，建议在写 `history.js` 之前先定。

### P1-7：错误边界缺失

没有 `GAME_STATUS.ERROR` 处理。全项目只有 `boot().catch`。`state.error` 字段存在但没有消费者。

`utils/invariant.js` 已经定义了完整的错误类型层次（`FateError` / `DeterminismError` / `UnknownContractError` / `ModLoadError` / `MapGenerationError` / `ContractViolationError`），把它们接到一个错误屏上是很自然的一步 —— 尤其是 `ModLoadError`，玩家装第三方模组失败时需要看得懂的提示。
### P2 档

- **`deepFreeze` 对 Map/Set 只冻结容器**，内部条目仍可增删。`shopStates`（`Map`）、`visitedNodeIds` / `clearedNodeIds`（`Set`）都在状态里，所以快照的不可变性是有洞的。要么补递归冻结，要么把注释改成如实描述。
- **`utils/ringBuffer.js` 是死代码**。`initialState.js` 的注释明确解释了为什么不用它（带私有字段的类实例无法被通用 `deepClone` 正确复制）。删掉，别留着误导人。
- **`public/audio/` 不存在**，`SOUND_MANIFEST` 里的条目全部 404。要么补音频资源，要么把清单裁到实际拥有的文件。
- **`src/mods/dev/` 目录不存在**，但 loader 已支持它（以最低优先级加载）。补一个示例模组价值很高 —— 它同时就是模组作者的文档。
- **无 README**。
- **`dist/` 是过期产物**（构建时间早于多个源文件的最后修改时间），别拿它判断当前状态。建议删掉并确认已在 `.gitignore` 里。
- **`store.js` 没有 `reset()`**，「回主菜单再开新游戏」需要重建整个 store，接线时会碰到这个坎。

## 七、测试缺口

现有 9 个测试文件覆盖的是 core 层。缺口按价值排序：

1. **`GameFlow` 探索流程零测试** —— `moveTo` / `descend` / `useRest` / `purchase` / `getEvent` / `resolveEvent` / `equip` / `salvage` / `enhance` 全部没有测试。这就是 P0-3 那个 bug 能活到现在的原因，也是接线时最容易踩雷的区域。**建议第一优先补这块**，因为接线工作会大量调用这些方法。
2. **`scheduler.stepEntity` 无直接测试** —— 只被战斗整体测试间接覆盖。oGCD 抢占和平局打破是确定性的核心，值得单测。
3. **UI 层零测试** —— screens / router / shell 全无。至少给 router 的 `go()` 加测试，它能立刻抓出 codex/history 缺失那一类问题。jsdom 下测 screens 的 DOM 结构与回调是可行的。
4. **audio throttle 无测试**。

跨速度对拍测试已经有了，改引擎时务必保持它绿。

## 八、推进路线建议

我会这样排：

**第一天** —— `git init` 建基线；补 `GameFlow` 探索流程测试（顺手把 P0-3 的 bug 表现固化成失败用例）；修 P0-3。

**第一周** —— 按 P0-1 的六步顺序接线阶段 9，一步一验证。CSS 同步补（每接一屏就补它的样式，不要攒到最后）。补 `codex.js` / `history.js`（写 history 前先定 P1-6 的胜利条件）。

**第二周** —— 清 P1：settings 消费、解锁生效、battle 动作、对话框三修、暂停、错误边界。删死代码（`panel/`、`layout.js`、`ringBuffer.js`、旧 `summary.js`）。

**之后** —— 音频资源、`mods/dev` 示例模组、README、宝珠系统的去留决策、响应式补全、无障碍（ESC / 焦点陷阱 / aria）。

一条经验：**接线过程中每完成一屏就跑一次 `npm run verify`**。跨速度对拍测试是你唯一能自动发现「UI 改动破坏了确定性」的手段，别让它长时间处于红灯。
